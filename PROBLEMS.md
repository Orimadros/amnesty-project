## 1) Magic-file dependency in the CAR builder (BLOCKING)

**Affected file:** `code/01_build/01_car/0_build_car_layers_from_raw.R`

The CAR builder declares four required raw inputs at lines 82–85. Three are legitimate raw downloads, but one is not:

- `data/input/sicar/car_combined_amazonBiome2.shp` — **not present, not raw, not produced by any script in this repo.**

The script `stop()`s at lines 89–98 if the file is absent, so the CAR module cannot run end-to-end until this file is generated by something in this repo (or accepted as a snapshot input with explicit provenance documentation).

### 1.1 Producer chain in legacy

The producer is in `legacy_repo/code/2_empirics.R`, lines 255–307. It is a two-stage chain:

**Stage 1 — combine cleaned per-state CAR shapefiles into one (lines 255–266).**

```r
file_name <- list.files(
  path = "/Users/.../amazonLandPrices_project/data/processing/CleanCARShapes_robust/",
  pattern = "*.shp", recursive = TRUE)
car <- data.frame()
for (f in file_name) {
  s <- read_sf(paste0(".../CleanCARShapes_robust/", f))
  car <- rbind(car, s)
}
# st_write(car, "~/car_combined.shp")     # commented out — was run once on Pedro's machine
```

The input `CleanCARShapes_robust/*.shp` is described in legacy comments (lines 257–258) as "fully 'cleaned' version by Thiago, fully validated; not dealing with overlaps or related issues."

**Stage 2 — intersect with the Amazon biome (lines 270–307).**

```r
car_1 <- car %>% filter(COD_ESTADO %in% c("AC","AM","RR","AP"))   # already entirely inside biome
car_2 <- car %>% filter(!COD_ESTADO %in% c("AC","AM","RR","AP"))  # need intersection
car_3 <- car %>% filter(COD_ESTADO == "PA")
# Parallel chunked st_intersection(amazon_bioma, ...) over 80 cores
ps <- rbind(pdfs, pdfs2, pdfs3, pdfs4, pdfs5, s1, s2, s3)
ps <- rbind(car_1, ps %>% dplyr::select(-id, -bioma))
# st_write(ps, "~/Documents/car_combined_amazonBiome2.shp")     # commented out — was run once
```

In legacy both `st_write` calls are commented out; lines 267 and 309 read pre-existing artifacts from Pedro's Dropbox (`amazon_working/amazon/car_combined.shp` and `amazon_project/data/intermediate/car_combined_amazonBiome2.shp`). Those files were generated once on Pedro's machine and never regenerated since.

### 1.2 Why this is not just a one-script migration

Stage 1's input — `CleanCARShapes_robust/*.shp`, Thiago's "robust cleaning" — has **no producer in `legacy_repo/`.** A `grep -rn "CleanCARShapes_robust"` over the legacy tree returns only this consumer site in `2_empirics.R`. Thiago's cleaning code is not in the repo.

So even after lifting `2_empirics.R:255-307` into the new repo, the chain still bottoms out on a black-box upstream cleaning step. The actual raw SICAR data on disk is at `data/input/sicar/shapefiles/{AC,AM,AP,MA,MT,PA,RO,RR,TO,...}/` (per-state SICAR registry downloads), but Thiago's cleaning sits between those and `car_combined.shp`.

### 1.3 Decision (2026-05-05): postpone

Migration of the magic-file producer is **postponed**. The CAR module will not run end-to-end in the new repo until either:
- Thiago's `CleanCARShapes_robust` cleaning code is recovered and migrated as a stage 0 of the CAR module, or
- Thiago's cleaned shapefiles are obtained as a snapshot and explicitly accepted as a "given" input (documented like the IBGE muni shapefile), or
- A decision is made to skip Thiago's cleaning entirely and feed `data/input/sicar/shapefiles/{state}/` straight into Stage 1.

Until one of those resolves, **everything downstream of the CAR module is also blocked** per the gradual-migration rule (VTN 6–8, Lavoura, NB/VNP, the entire Pedro track).

### 1.4 Clarification (2026-05-06): `1_mapbiomas` has many dangling/hardcoded fragments, but most are recoverable

`legacy_repo/code/1_mapbiomas.R` is messy and mixes pipeline code with exploratory blocks and hardcoded personal paths. That creates many apparent "magic files" at first glance.

Important clarification:
- For the core computational backbone, most derived artifacts consumed there **do have generation logic in-repo**, but it is split across scripts and needs cleanup/re-wiring.
- `transitions_combined/*.tif` is generated in `legacy_repo/code/1_mapbiomas.R` itself (writes to `data/processing/transitions_combined`).
- `car_all_cleaned.shp` and `car_eligible_cleaned.shp` are generated in `legacy_repo/code/2_empirics.R` (they are read as external inputs in `1_mapbiomas`, but their producer logic exists in-repo).
- `control_areas2` in `1_mapbiomas` is a dangling legacy object; the active control-area construction logic is `control_areas` (from CNFP raw + biome intersection), present in `2_empirics`.

So, with code hygiene (path normalization, removal of exploratory blocks, explicit DAG edges), these artifacts are reproducible from raw sources in this repo's codebase.

The main unresolved exception remains:
- `CleanCARShapes_robust/*.shp` has no producer script in-repo and is still the critical upstream bottleneck.

Note on `mapbiomas_amazon_official.xlsx`:
- It is an external benchmark table used for comparison plots in late `1_mapbiomas` sections, not required to generate the core `transitions_combined` outputs.

## 2) Non-idempotent step in the migrated VTN chain

**Affected file:** `code/01_build/02_vtn/3_unmatched_vtn_correction.R` (lines 105–108).

The script asserts `row_diff == -1` for 2015 (the bogus `EX / EXTERIOR` row removal) and `row_diff == 0` for other years. On a re-run against an already-patched 2015 file, the EXTERIOR row is already gone, so `row_diff == 0`, and the script `stop()`s.

Detailed write-up and proposed invariant-based fix in `legacy_repo/PROBLEMS.md`, section 6A. **Not fixed in this round** — flag only.

## 3) Manual fix-sheet inputs (in scope, working as designed)

`code/01_build/02_vtn/3_unmatched_vtn_correction.R` consumes seven manual-correction CSVs at `data/input/manual/vtn/`:

```
unmatched_2015_TO_FIX.csv   (28 rows)
unmatched_2016_TO_FIX.csv   (5 rows)
unmatched_2017_TO_FIX.csv   (3 rows)
unmatched_2018_TO_FIX.csv   (4 rows)
unmatched_2019_TO_FIX.csv   (13 rows)
unmatched_2021_TO_FIX.csv   (14 rows)
unmatched_2022_TO_FIX.csv   (15 rows)
```

Each row maps `(state, mun_name)` to a `muni_code`, and the script fills in missing `muni_code` values in the cleaned VTN tables. The 2018 file additionally drives the ACEGUA `RR → RS` state-label fix; the 2015 file additionally drives the EXTERIOR row removal.

These are intentional, curated inputs. Listed here so the migration record is explicit about what hand-curated state the pipeline depends on.
